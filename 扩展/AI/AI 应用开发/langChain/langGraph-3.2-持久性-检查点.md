# langGraph-3.2-持久化-检查点(Checkpointers)

- LangGraph 提供了两种互补的持久化系统：
  1. Checkpointer 保存一次对话线程的图状态，
  2. Store 保存跨线程长期使用的数据。两者解决不同的问题，生产系统通常可以同时使用。

Checkpointer 不是简单地把对话保存到数据库，而是保存图执行过程中的状态快照及节点写入记录，让工作流能够恢复、暂停、回放和查看历史。

## 一、概念理解

### 1.1 六个核心概念

| 概念         | 含义                       | 你可以怎么理解             |
| ------------ | -------------------------- | -------------------------- |
| State        | 图当前的状态               | 工作流运行时的数据         |
| Thread       | 一条持久化执行历史         | 通常对应一次对话或一项任务 |
| Checkpoint   | 某个执行边界的状态快照     | 一张状态快照               |
| Super-step   | 一轮图调度                 | 一批被安排执行的节点       |
| Checkpointer | 负责读写检查点的组件       | 持久化适配器               |
| Writes       | 节点执行产生的中间写入记录 | 便于故障恢复的执行记录     |

1. Super-step 不是一个节点（node），也不是固定执行一次模型调用，而是 LangGraph 调度图执行时的一个“执行轮次”。

   一个 super-step 可以执行一个节点，也可以并行执行多个节点。它的分界主要由 `图的调度与节点执行状态` 决定，而不是由你手动数代码行数决定。
   - 真正决定分界点的是什么？
     1. ① Plan: 确定本轮执行谁: 根据当前状态和前一轮的更新，确定哪些节点需要运行。
     2. Execute: 执行本轮节点: 被调度的节点运行，可以并行；它们产生的更新在本轮执行期间不会立即成为其他节点可见的新一轮状态。
     3. Update: 应用本轮更新: 汇总并应用节点写入的更新，形成后续执行所依据的状态。
     4. 下一轮 Plan: 根据更新决定下一批要执行的节点

   super-step 的数量取决于实际执行路径，不是图上有多少条边，也不是节点总数。

2. Checkpoint vs Writes
   - Checkpoint: 保存某个 super-step 边界上的”完整状态快照“。
   - Writes: 保存同一轮中 “已经成功执行的节点“ 状态更新记录，供当前执行过程恢复使用。
   - Writes 不等于新的完整状态快照，它是 LangGraph 自己的节点级写入记录，能够帮助恢复时 避免重复运行已经成功的节点。
   - Writes 的保留、关联及清理由 Checkpointer 的具体实现和执行恢复机制决定，不能简单认为所有 Writes 都会永久保留，也不能认为每个新节点都会覆盖上一条。
   - 新节点产生新的写入记录，不等于覆盖旧记录；但旧 Writes 是否继续保留，要看其生命周期和 Checkpointer 的实现。

   | 对比项               | Writes                         | Checkpoint               |
   | -------------------- | ------------------------------ | ------------------------ |
   | 保存内容             | 节点级输出、特定任务的写入记录 | 完整 State 快照          |
   | 写入时机             | 节点完成时                     | super-step 完成时        |
   | 是否包含完整 State   | 否                             | 是                       |
   | 是否支持历史状态查看 | 辅助恢复，不是完整快照         | 是                       |
   | 核心作用             | 避免已成功节点重复执行         | 恢复某个执行边界上的状态 |

   Checkpoint 解决“恢复时，整个图的状态是什么”；Writes 解决“当前这轮中，哪些节点已经成功做完，它们的结果是什么”【存在并行情况】。
   核心区别: Checkpoint 记录完整状态；Writes 记录 节点执行过程中 已经成功完成的写入，以支持恢复。

### 1.2 为什么会不断产生检查点？

检查点不是定时保存的，也不是只在用户发送消息时保存的，而是主要由图执行过程中的调度边界触发。 同一 super-step 内，节点级 Writes 还会单独持久化。

1. 这里有两个不同的“叠加”:
   - State 内部的叠加: messages 使用 add reducer，因此新消息会累积到当前状态中。
   - Checkpoint 历史的叠加: 每次保存会产生新的检查点历史记录，旧记录通常不会自动被新记录替换。

   所以，检查点数量增加，和每个检查点中的数据越来越多，是两个不同的问题。

2. 期线程不仅可能占用更多磁盘，也可能增加历史查询、序列化和维护的成本。
   解决方向
   1. 控制 State 体积: 避免无必要地在 State 中重复保存大段文档、完整检索结果或大型对象。
   2. 限制会话历史: 结合消息裁剪、摘要和业务保留策略，减少每次快照中的累积数据。
   3. 选择合适的存储策略: 对大量追加型状态，评估增量存储能力。
   4. 实施历史清理: 根据业务保留期限清理旧线程或检查点，同时保证恢复和审计需求得到满足。

## 二、代码解读

定义了 State 并不等于启用了持久化，定义了图也不等于启用了持久化。需要给编译后的图配置 Checkpointer。

### 2.1 读取检查点

```python
# 获取最新状态
snapshot = graph.get_state(config)

print(snapshot.values)
print(snapshot.next)
print(snapshot.metadata)
```

StateSnapshot 不只保存业务状态，还包含下一步节点、检查点配置、执行元数据、父检查点和任务信息等。

- values: 当前快照的 State。
- next: 下一步计划执行的节点；空元组通常表示图已经结束。
- metadata: 执行来源、节点写入、step 等信息。
- parent_config: 前一个检查点的定位信息。

history = list(graph.get_state_history(config))

graph.update_state(

## 三、能力边界: 它能保证什么，不能保证什么？

Checkpointer 支持的核心用途。

| 能力              | 解决的问题           | 实际价值                     |
| ----------------- | -------------------- | ---------------------------- |
| Human-in-the-loop | 人工审核、批准、修改 | 高风险操作可暂停等待人处理   |
| Memory            | 多轮交互保留状态     | 同一 thread 可延续之前的对话 |
| Time travel       | 查看、回放历史执行   | 调试 Agent 为什么走到某一步  |
| Fault-tolerance   | 节点失败后恢复       | 尽可能复用已成功的节点结果   |

1. 持久化不等于永久记忆。

   Checkpointer 保存的是图状态，不会自动将所有业务知识整理成长期记忆，也不会自动为你实现用户画像、知识库检索或跨用户共享记忆

2. 恢复执行不等于外部操作只执行一次。

   例: 节点调用了一个支付 API，支付平台已经扣款，但服务在保存节点结果前崩溃。恢复时，节点可能再次执行。

3. 保存了状态不等于已经保存了所有运行环境。
   例: 数据库连接、HTTP 客户端、模型客户端、进程中的任意全局变量，并不会因为出现在某个 Python 进程中就自动成为可恢复的业务状态。

### 3.1 持久化的三种 durability 模式

1. exit: (性能优先) 图执行退出时才持久化更改。中途进程崩溃时，尚未保存的中间状态无法用于恢复。
2. async: (性能与可靠性折中) 持久化与下一步执行并行推进。性能较好，但崩溃时可能来不及写入最新检查点。
3. sync: (持久化优先) 在开始下一步之前同步完成检查点写入。可靠性更强，但会增加执行开销。

❗sync 强化的是检查点写入的时序保证，不代表整个业务事务具有原子性。外部 API 的成功与数据库写入之间，依然可能出现故障窗口。
