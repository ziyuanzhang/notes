## 1、yield：生成器的暂停/恢复机制

- 包含 yield 的函数称为“生成器函数（Generator Function）”。
- 调用生成器函数时，“不会立即执行函数体”，而是返回一个“生成器对象（Generator）”。
- 生成器对象是一种“迭代器（Iterator）”，可以通过 next()（或 for 循环）逐步获取数据。

```python
def gen():
    print("A")
    yield 1

    print("B")
    yield 2

    print("C")

  # 执行过程：
  # 调用：g = gen(); 此时：没有执行函数体 --> 得到 Generator 对象
  # 第一次：next(g); 执行：print("A") --> yield 1 --> 返回 1(暂停)
  # 第二次：next(g); 继续：从上一次 yield 后面继续 --> print("B") --> yield 2 --> 返回 2(暂停)
  # 第三次：next(g); 继续：从上最后一次 yield 继续 --> print("C") --> 函数结束 --> 抛出 StopIteration
  # ---------------------------------------------------------
  # yield --> 保存当前执行现场 --> 值交给调用方 --> 暂停 generator --> 以后 next() --> 从 yield 后面继续
```

⚠️

1. yield：不是线程切换。
2. 也不是：Event Loop 调度。
3. 它首先是 Python 的生成器控制流机制。

## 2、await：协程的挂起点

```python
   async def foo():
       print("A")
       await asyncio.sleep(1)
       print("B")

# 执行：foo() --> Coroutine Object (协程对象)

# --- 真正被 Event Loop 调度之后： ---
执行 print("A")
 ↓
await asyncio.sleep(1)
 ↓
如果需要等待
 ↓
当前 Task 暂停
 ↓
Event Loop 接管
 ↓
执行其他 Task
 ↓
1 秒后
 ↓
foo Task 重新进入 Ready 状态
 ↓
继续执行 print("B")
```

- await 是协程的重要 suspension point（挂起点）。
- await 提供了挂起协程的机会；是否真正挂起，取决于所等待的 awaitable 当前状态及其实现。

```python
async def foo():
    result = await already_finished_future
    print(result)
```

如果 Future 已经完成，可能不会产生实际的异步等待。

⚠️ 所以：await ≠ 100% 一定发生上下文切换

- await 等的是一个具体异步操作。

## 3、yield 🆚 await

|                         | `yield`               | `await`                |
| ----------------------- | --------------------- | ---------------------- |
| 所属模型                | Generator（生成器）   | Coroutine（协程）      |
| 主要目的                | 产生数据 + 暂停       | 等待异步操作           |
| 谁恢复                  | `next()` / 迭代器协议 | Event Loop / Task 调度 |
| 是否天然涉及 Event Loop | ❌                    | ✅                     |
| 是否线程切换            | ❌                    | ❌ 不代表线程切换      |
| 是否可以产生数据        | ✅                    | ❌ 本身不是产生数据    |
| 典型场景                | 数据流、迭代          | 网络、数据库、异步 I/O |

- yield 是“我给你一个值，然后先停一下”；
- await 是“我要等这个异步操作完成，先让我停一下”。

## 4、async def + yield：异步生成器

不是普通 generator，而是：异步生成器（Async Generator）

```python
   async def gen():
       yield 1
       yield 2

    # 执行
    async for x in gen():
       print(x)
    # 或
    g = gen()
    x = await anext(g)

   # 普通 generator： def --> yield --> Generator --> next()
   # async generator: async def + yield --> Async Generator --> async for / anext()

```

async def + yield 中的 yield 仍然是生成器语义，不等于 await

| 东西             | 本质作用               | 谁恢复                  |
| ---------------- | ---------------------- | ----------------------- |
| `yield`          | 暂停函数、保存现场     | 调用方/迭代器机制       |
| `next()`         | 恢复 generator         | 调用方主动调用          |
| `await`          | 等待 awaitable         | Event Loop/异步调度机制 |
| `lifespan yield` | 划分启动和关闭生命周期 | FastAPI 生命周期管理    |

## 5、FastAPI lifespan 中的 yield

```python
  from contextlib import asynccontextmanager

  @asynccontextmanager
  async def lifespan(app):
      print("启动")

      yield

      print("关闭")

    # 应用启动 --> 执行 yield 前代码 --> yield --> 应用运行 --> 应用关闭 --> 执行 yield 后代码
```

❗这里的 yield 可以理解成：生命周期的分界点。

1. yield 前 = startup
2. yield = startup 完成 / application running
3. yield 后 = shutdown

- lifespan 是通过 @asynccontextmanager 把"异步生成器" 包装成 "异步上下文管理器"。

```bash
   async def + yield +  @asynccontextmanager
       ↓
   异步上下文管理器
       ↓
   启动时执行 yield 前
       ↓
   运行期间保持上下文
       ↓
   关闭时执行 yield 后
```

## 7、Event Loop

Event Loop 是一个运行在某个线程中的事件循环，用于驱动和调度 asyncio Task，并监听异步 I/O、定时器、Future 等事件。

- 它是一个调度器（Scheduler）对象，它运行在线程里，不是线程；

⚠️ Event Loop ≠ Thread

- 它负责：
  - 创建、管理 Task
  - 调度协程（Coroutine）
  - 等待 I/O 完成
  - 恢复暂停的协程
  - 处理超时、取消等事件

- 可以创建多个Event Loop；但 一个线程，在同一时刻，最多只能有一个正在运行的 asyncio Event Loop。

```python
  import asyncio
  loop = asyncio.get_running_loop()
  # 这里得到的是：asyncio EventLoop 对象（asyncio.AbstractEventLoop）;
  # 不是：Thread 对象
```

```bash
Event Loop
    ↓
维护各种待处理事件 / Ready Task / I/O 回调
    ↓
选择下一项可运行工作
    ↓
运行
    ↓
再次调度
```

```bash
   # 执行过程：Main Thread --> Event Loop --> A -> await --> B -> await --> C -> await --> D -> await --> E -> await --> A恢复
   # 一个线程,很多协程
```

- 如果在执行C时，A的await有结果了, 是执行D还是执行A的结果？：

  Event Loop 会继续执行 Task C，直到 Task C 主动交出控制权（遇到 await 或执行结束），然后大概率会先执行 Task D，最后再处理 Task A 的结果（Event Loop 内部维护 Ready Queue。谁先进入 Ready Queue，谁先执行。）
  1. 核心机制：协作式多任务 (Cooperative Multitasking)

     Python 的 asyncio 属于**“协作式”**多任务，而不是像操作系统线程那样的“抢占式”多任务。
     - 抢占式（线程）： 操作系统可以随时强制暂停当前线程，把 CPU 分配给其他线程。
     - 协作式（协程）： Event Loop 绝对不可能强行中断正在运行的协程（Task C）。Task C 必须自愿交出控制权（通过执行到 await 关键字，或者函数 return 结束），Event Loop 才能重新接管 CPU 去调度其他任务。

  2. 场景重演：当 C 正在执行，A 的结果回来了

     我们一步步来看你的场景：
     1. 初始状态： Task A 遇到 await 发起了网络请求，把控制权交还给 Event Loop。Event Loop 调度了 Task B，B await 后，又调度了 Task C。
     2. 当前状态： CPU 正在全力执行 Task C 中的同步代码。
     3. 事件发生： 就在此时，Task A 等待的网络请求在操作系统底层（网卡/内核）完成了，数据已经准备好。
     4. 此时的 Event Loop 在干嘛？ 答案是：它什么都干不了。 因为此时 CPU 的控制权在 Task C 手里。Event Loop 本身也只是一段 Python 代码，它必须等待 Task C 把 CPU 还给它。

  3. 接下来会发生什么？(执行顺序)

     假设 Task C 继续执行，终于遇到了一个 await（或者执行完毕退出了）：
     1. 交出控制权： Task C 遇到 await，暂停自己，把控制权还给主线程的 Event Loop。
     2. Event Loop 检查状态 (Polling)： Event Loop 拿到控制权后，第一件事就是去检查底层操作系统（通过 epoll / kqueue 等机制），看看之前挂起的 I/O 操作有没有完成的。
     3. 发现 A 已完成： Event Loop 发现 Task A 的数据回来了。它会把 Task A 标记为“准备就绪 (Ready)”，并将其放入内部的**“就绪队列 (Ready Queue)”**的末尾。
     4. 调度下一个任务： Event Loop 检查“就绪队列”，看看谁排在最前面。
        - 在 C 执行期间，如果 Task D 已经被安排进队列等待执行，那么排在前面的会是 Task D。
        - Event Loop 会把控制权交给 Task D。

  4. 最终轮到 A： 等到 Task D 也遇到 await 交出控制权后，Event Loop 再次检查队列，此时终于轮到了之前被放入队列的 Task A，Task A 拿到结果，从上次 await 的地方继续往下执行。
  - 🍔 一个通俗的餐厅比喻
    - 把 Event Loop 想象成餐厅里唯一的一个超级厨师。
    - 把 Tasks 想象成不同的菜品订单。
    - 把 await 想象成把菜放进微波炉或者烤箱，需要等待。
      1. 厨师接了订单 A，把 A 放进微波炉（await），厨师闲下来了。
      2. 厨师赶紧去切订单 C 的洋葱（正在执行 Task C 的同步代码）。
      3. 就在厨师正在疯狂切洋葱的时候，“叮！”的一声，订单 A 的微波炉加热好了（A 的结果回来了）。
      4. 厨师会扔下手里切了一半的洋葱去拿 A 吗？绝对不会。
      5. 厨师必须把眼前的洋葱切完，放进锅里炖上（Task C 遇到了 await），他才能腾出手来。
      6. 腾出手后，他看了看挂着的订单(“现在有哪些工作已经 Ready？”)，发现订单 D 要求拌个沙拉，于是他先去拌沙拉（执行 Task D）。
      7. 等沙拉拌完，他再去微波炉里把订单 A 拿出来继续装盘（处理 A 的结果）。

- 如果遇到同步阻塞代码：

## 10、StreamingResponse + generator

对于同步 generator，Starlette 会使用线程池机制迭代它，避免同步 iterator 阻塞 Event Loop。

```python
  def generator():
      while True:
          chunk = get_chunk()
          yield chunk

  @app.get("/")
  def download():
      return StreamingResponse(generator())

# generator 并不天然绑定某一个线程。

Event Loop
    ↓
需要下一块数据
    ↓
Worker Thread
    ↓
next(generator)
    ↓
yield chunk
    ↓
Worker Thread 暂时结束这次执行
    ↓
Event Loop 获得 chunk
    ↓
发送数据
    ↓
需要下一块
    ↓
再次调用 next()

# 第一次 next() --> Thread 1, yield
# 第二次 next() --> Thread 3, yield
# 第三次 next() --> Thread 2, yield

```

- 线程不是一直被某个生成器独占。
- 每次只是短暂执行一次 next(generator)。
- yield 后生成器暂停，线程即可归还线程池。
- 下次继续执行生成器时，可能还是原来的线程，也可能是线程池中的另一个线程，生成器本身并不依赖固定线程。

## 13、铁律: 线程池 ≠ CPU 密集型任务解决方案

- 铁律 1：异步 I/O ---→ async def + await
- 铁律 2：同步阻塞 I/O ---→ 线程池
- 铁律 3：纯 Python CPU 密集 ---→ 不要指望线程池解决 GIL(多进程/进程池，释放 GIL 的计算库)。
- 铁律 4：不要阻塞 Event Loop
- 铁律 5：await ≠ 线程切换
  1. await --> 协程挂起 --> Event Loop 调度其他 Task
  2. 不是：await --> Thread 1 --> Thread 2
  3. 通常仍然是：同一个 Event Loop + 同一个线程 + 不同 Task 之间协作式切换

## 14、GIL（Global Interpreter Lock）： 是 CPython 的线程锁

- 传统 CPython 的主流执行模型: 它保证同一时刻,一个进程内,只有一个线程执行 Python 字节码；
- I/O 时: 很多阻塞 I/O 操作会释放 GIL
