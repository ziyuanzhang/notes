# HTTPS / TLS 工作原理：修正与整理版

> 核心结论：HTTPS = HTTP over TLS。现代 TLS
> 通过证书与数字签名验证服务器身份，通过（EC）DHE
> 等密钥交换机制建立共享秘密，再通过 HKDF
> 派生流量密钥，最后使用对称加密和完整性保护传输 HTTP 数据。

---

## 一、整体认识

### 1. SSL、TLS

- **SSL**：Secure Sockets Layer，安全套接层，是 TLS 的前身。❗SSL2.0、SSL3.0 已废弃。
- **TLS**：Transport Layer Security，传输层安全协议，是 SSL的后继协议。
  - 现在主要关注 **TLS 1.2 和 TLS 1.3**。❗TLS 1.0、TLS 1.1 已废弃。

### HTTPS 是什么

HTTPS = HTTP over TLS，即运行在 TLS 安全连接上的 HTTP。

TLS 为传输提供：

- 机密性：防止旁观者直接读取内容。
- 完整性：检测数据是否被篡改。
- 身份认证：通常通过证书验证服务器身份。
  HTTPS 常用端口 443，但端口可配置。

### 2. HTTPS 在协议栈中的位置

```text
HTTP        应用层：请求、响应、Headers、Body
TLS         安全层：身份认证、密钥协商、加密、完整性保护
TCP         传输层：可靠传输、连接管理
IP          网络层：寻址、路由转发
```

- HTTP 默认端口：80。
- HTTPS 默认端口：443。
- TLS 1.2/1.3 通常运行在 TCP 之上。
- HTTP/3 使用 QUIC；QUIC 内部集成 TLS 1.3，不再使用 TCP。

TLS 并不是简单地把 HTTP 数据"再加密一次"，而是在 HTTP与底层传输之间提供安全通信能力。

### 3. HTTPS 主要解决的问题

安全目标 主要机制 作用

---

身份认证 数字证书、证书链、数字签名 验证服务器身份
密钥协商 ECDHE 等密钥交换算法 让通信双方得到相同的共享秘密
机密性 对称加密 防止通信内容被窃听
完整性 AEAD 完整性认证标签等 检测数据是否被篡改

**记忆主线：证书认证身份，密钥交换建立共享秘密，密钥派生生成流量密钥，对称加密保护实际数据。**

## 二、三种核心密码学机制

### 1. 对称加密

**定义：加密和解密使用同一个密钥。**

例如，客户端和服务器都持有密钥 `K`：

```text
客户端                                      服务器
原始数据
   |
使用 K 加密
   |
密文  ------------------------------------> 密文
                                               |
                                           使用 K 解密
                                               |
                                             原始数据
```

特点：

- 加密、解密速度快，适合大量数据传输。
- 通信双方必须安全地获得相同的密钥。
- 如果密钥泄露，攻击者可能解密相应通信数据。

常见算法：

- AES-128 / AES-256
- ChaCha20

现代 TLS 常使用 AEAD 算法，例如：

- AES-GCM
- ChaCha20-Poly1305

AEAD 不仅提供机密性，还提供完整性和真实性校验。

### 2. 非对称密码学

**定义：使用一对数学上相关的密钥，通常称为公钥和私钥。**

- **公钥（Public Key）**：可以公开。
- **私钥（Private Key）**：必须保密。

需要纠正一个常见误区：公钥和私钥并不是在所有算法中都简单地规定为"一个只能加密、另一个只能解密"。不同算法具有不同用途。

#### 2.1 公钥加密、私钥解密

以支持加密的 RSA 用法为例：

```text
发送方                                  接收方
原始数据
   |
使用接收方公钥加密
   |
密文  --------------------------------> 密文
                                          |
                                      使用私钥解密
                                          |
                                        原始数据
```

作用：只有持有对应私钥的一方才能解密。

#### 2.2 私钥签名、公钥验证

```text
签名方                                  验证方
数据 / 握手上下文
   |
使用私钥生成数字签名
   |
签名  --------------------------------> 签名 + 原始数据
                                          |
                                      使用公钥验证签名
                                          |
                                      验证通过或失败
```

数字签名的核心作用：

- 验证签名是否由对应私钥生成。
- 检测被签名数据是否发生变化。
- 在证书和握手场景中，用于证明私钥持有关系。

**数字签名不等于加密。**签名通常不隐藏数据内容。

#### 2.3 不同算法的用途

---

算法类型 典型用途 说明

---

RSA 加密、数字签名 TLS 1.2 旧式 RSA 密钥交换曾使用 RSA 加密；现代 TLS
中 RSA 证书通常用于签名认证

ECDSA 数字签名 用于证明私钥持有关系

EdDSA 数字签名 例如 Ed25519

ECDHE 密钥协商 双方计算相同共享秘密，不是简单的公钥加密、私钥解密

---

### 3. 数字证书与 CA

CA（Certificate
Authority，证书颁发机构）负责验证申请信息并对证书进行数字签名。

常见公共 CA/证书服务包括 DigiCert、Let's Encrypt、GlobalSign 等。

#### 3.1 服务器如何获得证书

假设企业要为 `www.example.com` 配置 HTTPS：

1.  **服务器生成密钥对**
    - 公钥 `A`
    - 私钥 `B`
    - 私钥 `B` 由服务器保管，不能泄露。
2.  **服务器生成 CSR**
    - CSR 是证书签名请求。
    - 通常包含公钥、申请的域名或主体信息等。
    - CSR 通常由申请方使用对应私钥签名。
3.  **向 CA 申请证书**
    - CA 按证书类型验证域名控制权或组织身份等。
4.  **CA 签发证书**
    - CA 将域名、公钥、有效期等信息组织成证书。
    - CA 使用自己的私钥对证书内容进行数字签名。
5.  **服务器部署证书**
    - 服务器部署证书及对应私钥。
    - 私钥必须安全保存，不能发送给客户端或 CA。

**关键纠正：CA 不是使用自己的私钥加密服务器公钥，而是使用 CA
私钥对证书内容进行数字签名。**

#### 3.2 证书通常包含什么

- 域名信息，通常通过 SAN（Subject Alternative Name）表示。
- 服务器公钥。
- 证书颁发者。
- 有效期。
- 证书用途及其他扩展约束。
- CA 的数字签名。

#### 3.3 客户端如何验证证书

客户端通常不需要用户手动安装公共 CA
证书。浏览器或操作系统一般已经内置可信 CA 根证书。

收到服务器证书后，客户端通常会检查：

1.  证书签名及证书链能否验证到受信任的根 CA。
2.  证书是否过期或尚未生效。
3.  访问域名是否与证书 SAN 匹配。
4.  证书用途、约束等是否符合要求。
5.  在适用情况下，检查证书撤销状态或相关状态信息。

验证 CA 签名时：

- CA 使用自己的私钥签名。
- 客户端使用对应 CA 公钥验证。

客户端不是简单地"用 CA 公钥解密证书"，而是验证证书签名及证书链。

如果验证失败，浏览器通常会提示证书错误，阻止或警告用户继续访问。

#### 3.4 CA 的职责边界

可以把 CA 理解为"身份和公钥绑定关系的可信签发者"，但不能认为 CA
保证网站业务本身安全。

CA 主要负责：

- 按规则验证申请者身份或域名控制权。
- 签发证书并进行数字签名。
- 管理证书生命周期。

CA 不参与客户端与服务器之间的日常 HTTP
数据传输，也不保证网站没有恶意行为。

## 三、现代 HTTPS：TLS 1.3 完整通信过程

以下以 **TLS 1.3、证书认证、ECDHE 密钥交换**为例。

先区分两个过程：

- **TCP 三次握手**：建立可靠传输连接。
- **TLS 握手**：协商安全参数、认证服务器、建立会话密钥。

### 1. 第一步：TCP 三次握手

```text
客户端                         服务器
  |                              |
  | -------- SYN --------------> |
  | <----- SYN + ACK ------------|
  | -------- ACK --------------> |
  |                              |
  |       TCP 连接建立            |
```

此时 TCP 连接建立，但 TLS 身份认证和 TLS 会话密钥协商尚未完成。TCP
本身不提供 TLS 的加密保护。

### 2. 第二步：客户端发送 ClientHello

客户端发送 `ClientHello`，主要包含：

字段 作用

---

Supported Versions 支持的 TLS 版本
Cipher Suites 支持的密码套件
Client Random 客户端随机数
Supported Groups 支持的密钥交换群组
Key Share 客户端提供的临时密钥交换公钥
Signature Algorithms 支持的签名算法

例如，客户端生成一组临时密钥：

- 临时私钥 `a`
- 临时公钥 `A1`

客户端把 `A1` 放入 Key Share 发送给服务器。

注意：`A1` 是本次密钥交换使用的临时公钥，不是证书中的长期公钥 `A`。

### 3. 第三步：服务器发送 ServerHello

服务器收到 `ClientHello` 后：

1.  选择双方支持的 TLS 版本。
2.  选择合适的密码套件和密钥交换参数。
3.  生成自己的临时密钥对。
4.  计算共享秘密。

例如服务器生成：

- 临时私钥 `b`
- 临时公钥 `B1`

服务器在 `ServerHello` 中返回选定参数、`Server Random` 和自己的 Key
Share `B1`。

### 4. 第四步：通过 ECDHE 得到共享秘密

双方交换临时公钥：

- 客户端获得服务器临时公钥 `B1`。
- 服务器获得客户端临时公钥 `A1`。

然后分别计算：

```text
客户端：使用自己的临时私钥 a + 服务器临时公钥 B1
服务器：使用自己的临时私钥 b + 客户端临时公钥 A1
```

数学上可表示为：

```text
S = ECDHE(a, B1) = ECDHE(b, A1)
```

双方独立计算得到相同的共享秘密 `S`。

```text
客户端                                  服务器
临时私钥 a                              临时私钥 b
服务器公钥 B1                           客户端公钥 A1
    |                                       |
    |           ECDHE 计算                  |
    |                                       |
得到共享秘密 S                         得到共享秘密 S
```

网络中传输的是临时公钥，不是共享秘密
`S`。攻击者即使截获双方临时公钥，也不能仅凭这些公开信息在计算上可行的时间内推导出共享秘密。

ECDHE 的临时密钥应按握手生成并妥善销毁。使用临时（EC）DHE
可以提供前向保密：服务器长期私钥日后泄露时，过去已完成的会话通常仍不会因此被解密，前提是临时秘密没有泄露。

### 5. 第五步：服务器发送证书并证明身份

TLS 1.3 中，服务器在 `ServerHello`
之后发送的握手消息通常已经受到握手密钥保护。典型消息包括：

- `EncryptedExtensions`
- `Certificate`
- `CertificateVerify`
- `Finished`

它们的作用不同：

**Certificate：**

- 携带服务器证书链。
- 让客户端取得服务器身份信息及证书公钥。

**CertificateVerify：**

- 服务器使用证书对应的私钥，对握手上下文生成数字签名。
- 客户端使用证书中的公钥验证签名。
- 用于证明服务器确实持有证书对应的私钥，并将身份认证绑定到当前握手。

**Finished：**

- 基于握手密钥和握手消息摘要生成验证数据。
- 用于确认握手上下文完整性，并证明发送方掌握相应握手密钥。

客户端主要进行以下验证：

1.  验证证书链和 CA 签名。
2.  检查域名、有效期、用途等。
3.  使用证书公钥验证 `CertificateVerify`。
4.  验证 `Finished`。

因此要记住：

**证书负责建立"域名与公钥"的可信绑定；CertificateVerify
证明当前服务器持有对应私钥；Finished 验证握手过程并确认密钥。**

服务器证书私钥在现代 TLS 1.3
中主要用于签名认证，不用于解密客户端发送的共享秘密。

### 6. 第六步：通过 HKDF 派生会话密钥

双方已经通过 ECDHE 得到相同的共享秘密。TLS 1.3 使用 HKDF
密钥派生机制，结合握手上下文等材料，派生握手流量密钥和应用流量密钥。

概念上可以理解为：

```text
ECDHE 共享秘密
       |
       v
TLS 1.3 密钥调度 / HKDF
       |
       +---- 客户端握手流量密钥
       |
       +---- 服务器握手流量密钥
       |
       +---- 客户端应用流量密钥
       |
       +---- 服务器应用流量密钥
```

注意：

- 不是双方简单地直接把 `S` 当作最终加密密钥。
- 不是客户端和服务器所有方向都共用一个完全相同的流量密钥。
- TLS 1.3 的密钥派生过程比"两个随机数混合生成一个 master
  secret"更完整。
- `Client Random`、`Server Random` 是公开的握手参数，不是秘密密钥。

双方发送并验证 `Finished` 后，握手完成，进入应用数据传输阶段。

### 7. 第七步：使用对称加密传输 HTTP 数据

TLS 握手完成后，客户端发送 HTTP 请求：

```http
POST /api/login HTTP/1.1
Host: www.example.com
Content-Type: application/json

{"username":"admin","password":"123456"}
```

TLS 对 HTTP 数据进行保护，再通过底层传输发送。

服务器收到后：

1.  TLS 层验证数据完整性并解密。
2.  将 HTTP 明文数据交给 HTTP 层。
3.  HTTP 层解析请求。
4.  业务程序处理请求。
5.  响应数据交给 TLS 层加密保护。
6.  通过网络返回客户端。

至此，HTTPS 安全通信建立并持续进行。

## 四、对称加密、非对称密码学如何配合

### 1. 纯对称加密

客户端与服务器直接使用相同密钥：

```text
客户端                         服务器
   |                              |
   |       双方需要相同密钥 K       |
   |                              |
   | <---- 安全获得密钥 K -------->|
   |                              |
   |       使用 K 加密通信          |
```

问题：双方如何安全地获得相同密钥？

如果直接通过不安全网络传输密钥，攻击者可能截获密钥。因此需要安全的密钥建立机制。

### 2. 纯非对称加密

客户端使用服务器公钥加密，服务器使用私钥解密。

问题：

- 非对称运算通常比对称加密开销更大，不适合大量数据传输。
- 如果没有证书认证，客户端无法确认拿到的公钥是否真的属于目标服务器。

另外，公钥公开本身不是漏洞。知道公钥不意味着能推导出私钥。

### 3. 现代 HTTPS：证书认证 + 密钥协商 + 对称加密

可以概括为：

1.  使用证书链和数字签名验证服务器身份。
2.  使用 ECDHE 等密钥交换算法协商共享秘密。
3.  使用 HKDF 派生会话流量密钥。
4.  使用 AES-GCM 或 ChaCha20-Poly1305 等 AEAD 算法保护实际数据。

**不要把现代 HTTPS
简化成"先用服务器公钥加密一个对称密钥，再用服务器私钥解密"。**这描述的是旧式
RSA 密钥交换思路，不是 TLS 1.3 的典型工作方式。

## 五、纠正几个常见误区

### 1. `Client Random + Server Random = Master Secret`？

这是不准确的简化。

TLS 1.2 中：

- RSA 密钥交换：客户端生成 Pre-Master Secret，用服务器 RSA
  公钥加密；服务器用私钥解密。
- ECDHE 密钥交换：双方通过 ECDHE 计算 Pre-Master Secret。
- 随后结合随机数等材料，通过 TLS 1.2 的 PRF 派生 Master Secret。

TLS 1.3 使用 HKDF 密钥调度，从密钥交换秘密、可选 PSK
和握手上下文等派生不同阶段的密钥，不再使用 TLS 1.2 的 Master Secret
派生模型。

### 2. 黑客知道公钥，就能破解非对称加密？

错误。

公钥本来就是公开的。非对称密码学的安全性建立在特定数学问题的计算困难性上。

例如：

- RSA：与大整数分解困难性相关。
- ECC：与椭圆曲线离散对数问题相关。

知道公钥不代表能在现实可行的时间内计算出私钥。

### 3. 对称加密比非对称加密更容易暴力破解？

不能这样简单比较。

两者使用不同的数学结构，安全性取决于算法、密钥长度、实现和使用方式。

例如：

- AES-128 的密钥空间为 `2^128`。
- AES-256 的密钥空间为 `2^256`。

合理使用时，暴力破解在现实中不可行。对称加密的主要优势是性能高，适合大量数据传输，而不是因为它安全性较低。

### 4. 客户端是否需要手动安装证书？

通常不需要。浏览器或操作系统一般已经内置可信 CA 根证书。

可能需要额外配置的情况：

- 企业内部使用私有 CA。
- 内网 HTTPS 使用内部证书体系。
- 特定设备使用自签名证书。
- 双向 TLS（mTLS）要求客户端提供客户端证书。

### 5. CA 是否保证网站安全？

不保证网站业务本身安全。

CA
主要证明证书中的身份与公钥绑定关系符合签发规则。它不能保证网站没有漏洞、没有恶意代码，也不能保证网站运营者值得信任。

### 6. TLS 是否只能运行在 TCP 之上？

不是。

TLS 1.2/1.3 通常用于 TCP 连接。HTTP/3 则运行在 QUIC 之上，QUIC 集成 TLS
1.3 的握手和密钥机制，不使用 TCP。

```text
  + Client Key Share

                                      ServerHello
                                      + Server Key Share

                                      Certificate

       ------------------------------------>

       开始加密应用数据传输
```

说明：

- `Certificate`：提供证书链。
- `CertificateVerify`：证明服务器持有证书对应的私钥。
- `Finished`：验证握手消息完整性并确认密钥。
- TLS 1.3 完整握手通常为 1-RTT；还存在会话恢复和 0-RTT 等机制，但
  0-RTT 数据具有重放风险，需要谨慎使用。

## 七、最终知识体系总结

```text
HTTPS = HTTP + TLS

1. TCP 连接
   └── TCP 三次握手，建立可靠传输连接

2. TLS 握手
   ├── ClientHello
   │   ├── 支持的 TLS 版本
   │   ├── 密码套件
   │   ├── Client Random
   │   └── 客户端临时 Key Share
   │
   ├── ServerHello
   │   ├── 选择 TLS 版本和密码套件
   │   ├── Server Random
   │   └── 服务器临时 Key Share
   │
   ├── ECDHE
   │   └── 双方计算相同的共享秘密
   │
   ├── 服务器身份认证
   │   ├── Certificate：证书链
   │   ├── CertificateVerify：私钥签名证明
   │   └── 客户端验证证书链、域名和签名
   │
   ├── HKDF
   │   └── 派生握手密钥和应用流量密钥
   │
   └── Finished
       └── 确认握手完整性和密钥

3. TLS 加密数据传输
   ├── 对称加密：保护机密性
   ├── 完整性认证：检测篡改
   └── 客户端与服务器使用各自方向的流量密钥

4. HTTP 业务通信
   ├── HTTP 请求
   ├── 服务器业务处理
   └── HTTP 响应
```

### 核心概念速查表

概念 解决的问题

---

CA 谁来证明服务器证书可信
数字证书 服务器身份与公钥的绑定
数字签名 验证签名来源及数据完整性
公钥 公开的密码学密钥材料
私钥 需要保密的密码学密钥材料
ECDHE 双方如何得到相同的共享秘密
HKDF 如何从秘密材料派生会话密钥
AES-GCM 如何加密数据并验证完整性
TLS 如何把认证、密钥协商和数据保护组织成安全协议
HTTPS 使用 TLS 保护 HTTP 通信

### 一句话总结

**客户端先通过 CA 证书验证服务器身份，再通过 ECDHE
等机制协商共享秘密，使用 HKDF
派生会话密钥，最后通过对称加密和完整性保护机制安全传输 HTTP 数据。**

## 八、自主可控性

HTTPS/TLS 是开放标准，不依赖某一家厂商。可以自主选择：

- TLS 实现：OpenSSL、LibreSSL、BoringSSL
  等（需关注各自维护状态、平台适配和许可证）。
- 企业内部 CA / PKI：可以自行部署和管理。
- 证书与私钥：可以自行管理、轮换和续期。
- TLS 版本、密码套件和安全策略：可以按兼容性和安全要求配置。

不需要绑定某一家云厂商才能实现 HTTPS。
